SemNav
Semantic-Aware Autonomous Navigation with YOLO, ONNX Runtime, LiDAR and Nav2 on ROS
2


Purpose of this document: a complete architecture reference you can hand to Claude Code and build from in roughly 7-10
working days, while ending up with something that reads as real robotics engineering rather than a tutorial replay.
One-line pitch: a mobile robot that detects objects with a camera, localises them with LiDAR, and feeds them into the Nav2
costmap through a custom C++ costmap-layer plugin, so the robot plans around what things are, not just where there is
something solid. A C++ safety gate sits between Nav2 and the wheels.


1. Why this project is a good pick
• It touches the whole stack: perception, sensor fusion, localisation, planning, control, safety, tooling. Interviewers can
   probe any layer and you have an answer.
• The differentiator is small but real: a custom nav2_costmap_2d plugin plus camera-to-LiDAR bearing fusion. Most
   student projects only run stock Nav2 or only run YOLO. Joining the two is the part that shows depth.
• Everything is measurable: inference latency, localisation error against Gazebo ground truth, navigation success with and
   without the semantic layer. Numbers on a README beat adjectives.
• Scope is controlled: no warehouse, no business logic, no manipulation. Everything lives in simulation, so it is
   reproducible and demoable from a laptop.
• Honest caveat: I do not know xboom's exact focus areas. Check their site and tweak the demo framing (for example,
   emphasise latency if they do embedded work, or the safety gate if they build AMRs).

Reading the diagram: orange "C++" tags mark the nodes you write. Blue is stock Nav2 configured by you. Purple is stock
localisation. Detections flow top-left to the costmap; the LiDAR is used twice (by Nav2's obstacle layer and by the fusion
node), which is deliberate: LiDAR stays the authority on geometry, the camera only adds meaning.

Data flow in six steps
• Camera frame arrives; yolo_onnx_node keeps only the newest frame, runs ONNX inference, publishes
   vision_msgs/Detection2DArray and an annotated image.
• semantic_fusion_node converts each bounding box to a bearing using camera intrinsics and the camera-to-laser TF, then
   reads the matching range from the latest /scan.
• The resulting point is transformed into the map frame, tracked across frames (nearest-neighbour + smoothing +
   time-to-live) and published as SemanticObstacleArray.
• SemanticLayer, a plugin inside both Nav2 costmaps, paints class-specific cost discs (for example a wide, high-cost bubble
   around a person, a small one around a chair).
• Nav2 plans and controls against the combined costmap and publishes /cmd_vel_nav.
• safety_gate_node limits or zeroes the command based on live LiDAR distance and publishes the final /cmd_vel to the
   robot.

7. Node specifications

7.1 yolo_onnx_node (C++, the performance-critical node)
 Aspect            Design

 Pipeline          Letterbox to 640x640 (keep aspect, pad grey 114) -> BGR to RGB -> float32 /255 -> NCHW tensor -> Ort::Session::Run ->
                   decode -> NMS -> undo letterbox -> publish.

 Decode            YOLOv8 output is [1, 84, 8400]: 4 box values (cx, cy, w, h) + 80 class scores per anchor, no objectness. Transpose, take
                   max class score, filter by conf_threshold (0.35), then cv::dnn::NMSBoxes (IoU 0.45).

 Concurrency       Subscriber callback only stores the newest cv::Mat under a mutex and signals a condition variable. A worker thread runs
                   inference. Old frames are dropped instead of queued, so latency never grows.

 ORT options       intra_op_num_threads (param, default 4), GraphOptimizationLevel ORT_ENABLE_ALL, pre-allocated input buffer reused
                   every frame, optional CUDA execution provider via param use_cuda.

 Parameters        model_path, conf_threshold, iou_threshold, input_size, class_filter (list of COCO names to keep, e.g. person, chair, bottle),
                   use_cuda, publish_annotated.

 Metrics           Time each stage (preprocess, infer, postprocess) with std::chrono, log rolling p50/p95 every 5 s, publish on /metrics.

 Tests             GoogleTest: letterbox round-trip maps a known box back to within 1 px; decode on a synthetic tensor returns the planted
                   box; NMS removes a duplicate.


7.2 semantic_fusion_node (C++, the clever bit)
 Aspect            Design

 Why               The Waffle has a 2D LiDAR, so full pixel-to-point projection is impossible. Instead use the bbox's horizontal span as an
 bearing-range     angular sector and read ranges from that sector. It is simple, robust and easy to explain.

 Algorithm         1) For bbox [u_min, u_max] build rays r = ((u-cx)/fx, 0, 1) in the optical frame. 2) Rotate rays into the laser frame with TF at
                   the image stamp and get yaw angles. 3) Collect scan ranges inside the central 60% of that sector. 4) Reject invalid /
                   out-of-range values, take the median (robust to wall pixels leaking in). 5) Position = range * (cos yaw, sin yaw), pad by class
                   radius. 6) Transform to map.

 Time sync         Look up TF at the detection stamp, and pick the scan closest in time (cache last N scans in a ring buffer). Use
                   message_filters ApproximateTime if you prefer, with slop 0.1 s.

 Tracking          Nearest-neighbour association by class and distance gate (0.6 m), exponential smoothing of position, id assignment, miss
                   counter; obstacle expires after ttl (default 2 s) so ghosts vanish.

 Outputs           SemanticObstacleArray plus MarkerArray (cylinder radius from class table, colour by class, text label with confidence).

 Parameters        class_radius map (person 0.35, chair 0.25, default 0.3), min/max_range, sector_fraction, assoc_gate, ttl, smoothing_alpha.

 Known limit       Objects not at the LiDAR height (a table top) can be missed or mis-ranged. State this in the README; it shows you
                   understand the model.


7.3 SemanticLayer (C++ nav2_costmap_2d plugin)
 Aspect            Design

 Base class        nav2_costmap_2d::Layer, exported with PLUGINLIB_EXPORT_CLASS and a plugin.xml; added to both global and local
                   costmaps in nav2_params.yaml.

 Lifecycle         onInitialize: declare params, subscribe /semantic_obstacles. updateBounds: expand the dirty window around each live
                   obstacle. updateCosts: paint into the master grid. reset(): clear cache.

 Cost model        Per class: core radius = LETHAL, then exponential decay out to class_inflation (person 1.0 m, chair 0.3 m, default 0.2 m)
                   using cost = 252*exp(-k*(d-r)). Combine with std::max so you never lower an existing cost.

 Thread safety     Subscription thread writes into a snapshot under a mutex; costmap thread copies it at the start of updateBounds.

 Frames            Obstacles are in map; use tf_ to convert to the costmap's global frame if rolling window is used.

 Why it matters    Without it, a person and a trash can look identical to the planner. With it, the robot leaves a wider berth around people. That
                   is a concrete, testable behaviour.


7.4 safety_gate_node (C++, control)
 Aspect            Design

 Inputs / output   Subscribes /cmd_vel_nav and /scan; publishes /cmd_vel at a fixed 20 Hz timer, never directly from the callback.

 Logic             Minimum range in a forward cone (default +/-30 deg, widened with angular speed). Scale factor s = clamp((d -
                   d_stop)/(d_slow - d_stop), 0, 1). Output v = s * v_cmd; angular velocity is kept so the robot can still turn away.

 Watchdog           If no /cmd_vel_nav for 0.5 s or no /scan for 0.3 s, publish zero. Acceleration limiter (max delta v per tick) avoids jerk.

 Be ready to        How it differs from nav2_collision_monitor (Nav2 ships one). Honest answer: this one is a deliberately small custom
 explain            implementation to show control-layer reasoning; in production you would evaluate the stock package first.

 Tests              Feed a synthetic scan with a wall at 0.3 m and check output is zero; feed far scan and check passthrough.


7.5 eval_logger_node (C++ or Python, small)
• Logs inference p50/p95 latency and FPS from /metrics.
• Compares fused obstacle positions against Gazebo ground truth to give mean localisation error per class.
• Sends a fixed list of goals through NavigateToPose and records success, time, path length, minimum clearance to people.
   Writes CSV for the results table.


8. Nav2 configuration decisions
 Area                      Decision

 Localisation              Mode A (default for demos and eval): pre-saved map + AMCL + map_server. Mode B (mapping demo): slam_toolbox
                           online_async to build the map, then save with map_saver.

 Global planner            SmacPlanner2D (or NavFn if you want fewer moving parts).

 Controller                DWB is the safe default. MPPI is more impressive if time allows; the change is one YAML block.

 Costmaps                  Global: static, obstacle (LiDAR), semantic, inflation. Local: rolling window 3x3 m, obstacle, semantic, inflation. Keep
                           semantic before inflation.

 Topic remap               Controller cmd_vel output remapped to /cmd_vel_nav so only the safety gate talks to the robot.

 Recoveries                Default BT with spin, backup, wait. Do not write a custom BT unless you finish early.

 - Build: colcon build --symlink-install --cmake-args -DCMAKE_BUILD_TYPE=Release
 - Test:   colcon test --event-handlers console_direct+

 - Keep pure logic (letterbox, decode, NMS, projection, cost math) in header-only classes
   with no ROS dependency so they are unit-testable.
 - After every change: build, run relevant tests, and show me the command output.
 - ONNX Runtime lives in third_party/onnxruntime (see scripts/setup_ort.sh).
 - Never add dependencies without asking. Small commits with clear messages.
 - Architecture source of truth: docs/SemNav_Architecture.pdf

Questions to rehearse
• Why fuse by bearing and range instead of projecting LiDAR points into the image?
• What happens when YOLO and LiDAR disagree, or when the detection is stale?
• Why drop frames rather than queue them? What QoS did you choose and why?
• How does your costmap layer avoid data races, and how do you clear ghost obstacles?
• How does your safety gate differ from nav2_collision_monitor?
• What would change on a real robot (calibration, time sync, 3D LiDAR, TensorRT, real-time executors)?
